# Architecture rules
- Manual alert evaluations use the existing authenticated backend without snapshots; persist only the pending empty request/key per API project and user, never retry POST automatically, recover jobs on entry and poll active jobs with server pacing; renew the alert snapshot only after global success.
- Operational alert diagnostics and secondary filters use progressive disclosure; keep freshness and data-quality warnings visible and preserve server-owned detection and review contracts.
- Alert situation labels use only conditionStatus, never conditionActive alone; display currentRule and lastEvaluation separately from positive-detection version/priority to avoid presenting historical evidence as a confirmed current result.
- Alert reassignment resolves canonical roles from the authenticated catalog and queries active users by each permitted role before pagination; merge and paginate only eligible candidates, never scan customer pages. Guard fresh submissions with the tested status/role predicate while retaining uncertain retry bodies, because server authorization remains authoritative.
- Alert review renders detection evidence only through a shared presentation adapter because current evidence is incomplete; translate request states and bank account types, preserve missing historical evidence, and never infer account equality from masked numbers. The trigger explanation presents the server reason and rule-specific review guidance, never an inferred field-level cause.
- Operational alerts use only backoffice-alerts endpoints with a shared server snapshot isolated by session/permissions; discard the whole cut on expiry or mutation, retain uncertain write keys/bodies, and keep detection and payment authorization server-side.
- Financial contacts use an independent authenticated CRUD client and identity-scoped queries; gate their settings section on ADMIN in backend-derived roles (normalize role.name/normalizedName when roles is absent, preserve explicit empty roles), never page grants or calculator membership; redirect the legacy standalone URL to the settings tab to preserve bookmarks; server authorization remains authoritative.
- Wide operational lists opt into shared Table horizontal-scroll mode with an always-visible upper slider synchronized to the native scroll viewport, so OS-hidden scrollbars cannot hide navigation; other tables and mobile cards retain their existing presentation.
- Bulk bank-data emails use publicId for detail and resend endpoints, paginated explicit selection and sequential writes without retries; select-all reads every filtered page atomically and detail links open a new tab to preserve the batch. Known already-processed cases warn and continue, real failures stop, and a failed preflight is never marked as an attempted email. Responses do not certify inbox delivery.
- Policy-number entry forms share the portability rule and immediate accessible warning; the frontend update client also rejects blocked policy payloads before sending them, so alternate entry paths cannot bypass the same restriction.
- Refund institution is read-only in backoffice edit dialogs (displayed with the catalog label, never editable); canonical values are lowercase and legacy values are shown as-is without migration.
- Dashboard comparison indicators share one presentation component with semantic theme tokens so summaries, insurance groups and pipeline variations remain visually consistent without changing calculations.
- Auth context identity lives in a component-free store and survives Vite hot updates, so refreshed route consumers never detach from the mounted provider.
- Dashboard indicators consume only the six aggregated backoffice-dashboard endpoints; operational alerts mount independently under Operación with their own filters and backoffice-alerts endpoints, so alerts-only access never grants operational reports or Dashboard metrics; all metric and detection rules remain in the backend.
- Dashboard queries are isolated by identity, permissions, endpoint, date range and series granularity; auth transitions and access denial cancel and remove only dashboard queries to prevent protected cache leakage without changing Operación.
- Dashboard adapters preserve backend totals, insurance tickets/shares and final series order/buckets; per-block query states distinguish failures from valid empty results.
- API clients and auth share an environment-configured API base URL; existing services keep their legacy default, but the dashboard requires an explicit environment value to prevent silent fallback.
- Bulk bank submission uses the existing refund status API and separate CSV rules/wizard, keeping document prerequisites but no AI validation dependencies, to preserve the bank trigger without affecting individual validation; it accepts both docs_pending and submitted as source states, forces only the latter after re-reading state, and displays statuses with Spanish labels.
- Bulk status services share an actor-attributed note builder using the current session and reject unidentified executors, so bank submissions and payments consistently record who initiated the batch without changing individual updates.
- Bulk status writes are sequential and stop on uncertain failures without automatic retries, because the API response does not confirm n8n completion.
- Bulk bank results read the current refund state with bounded read-only polling and manual refresh; the initial write response is not the final state and a SUBMITTED read does not certify n8n completion.
- Shared app flex columns use min-w-0; wide tabs and tables scroll within their own containers so mobile layouts cannot widen the document.
